- Adds a Tandem-only built-in `imagegen` tool (generate or edit raster images via OpenAI), self-contained in its own directory and contributed through the existing plugin `tool` hook so no upstream tool/registry files change; registered in `internalPlugins()` (one import + one array entry, both `UPSTREAM-DIVERGENCE`). - Two transports by auth mode (resolved at execute time): **API key** (`Auth` store `openai` type `api`, or `OPENAI_API_KEY`) → REST `POST api.openai.com/v1/images/{generations,edits}` with model `gpt-image-2` (generations JSON, edits multipart, `data[].b64_json`); **ChatGPT OAuth** (`openai` type `oauth`) → the OpenAI Responses built-in `image_generation` tool over `POST chatgpt.com/backend-api/codex/responses` (the ChatGPT backend has no REST images route), with `stream:true`+`store:false`, `tools:[{type:"image_generation",size,quality,output_format:"png",moderation:"low"}]`, `tool_choice` forced, edits via `input_image` data-URL parts; the base64 PNG is read off the SSE `response.output_item.done` (`item.result`). The OAuth `instructions` force exact pass-through of the user's wording. Separately, the prompt the image model reports it actually used (`revised_prompt`) is captured per image — on OAuth from the SSE `image_generation_call` item, on the API-key path from `data[].revised_prompt` — threaded through `run()`/`execute` into `metadata.revisedPrompt` and appended to the tool `output` only when it differs from the typed prompt.  - Output keeps the image out of the model's context: the tool result is path-only text `output` — no attachment and no image in `metadata`.  - Honest size reporting (OAuth ignores `size`): on the ChatGPT/OAuth backend the `image_generation` tool **ignores the requested `size`** entirely — the host model auto-sizes from the prompt and even returns non-enum dimensions (live-probed: a landscape prompt at `size:1024x1024` → 1536x1024; a portrait config on the same prompt → still 1536x1024; a square-cued prompt → 1254x1254; and an end-to-end `run()` → 1402x1122). A forceful size `instructions` directive does **not** help (unlike the verbatim-prompt trick), so on OAuth the result can differ from the request. `ImageGen.pngDimensions(buf)` reads the real width/height from each PNG's IHDR header, and `plugin.ts` reports those **actual** dimensions in the output label and `metadata.size`, adds `metadata.requestedSize`, and appends a one-line note when an OAuth request's size was dropped (so the agent doesn't retry the same size). Bytes are requested as PNG from both backends; `encodeJpeg` recompresses it to JPEG at the same pixel dimensions via the already-bundled Photon WASM codec (`PhotonImage.new_from_byteslice` → `get_bytes_jpeg`, the same lib `Image.normalize` uses — no new dependency), returning undefined (PNG-only) when Photon can't decode the buffer or the JPEG isn't smaller, so the optimization can't break saving. Quality (1–100, default 90) is set by `TANDEM_IMAGEGEN_JPEG_QUALITY`. For transparent images the chat copy is **WebP** instead (`encodeWebp` → Photon `get_bytes_webp`, alpha preserved — JPEG can't), so `saveImage(png, dir, base, transparent)` writes `<stem>.png` + `<stem>.webp`. `file.read`/`read` identify each copy by magic bytes (`ff d8 ff` → jpeg, `RIFF…WEBP` → webp; `util/media.ts`, `read.ts` `SUPPORTED_IMAGE_MIMES` already includes webp), and size reporting reads the original PNG headers, so dimensions stay accurate. The Photon loader was extracted to a shared `photon.ts` (`loadPhoton`, mirrors the `__OPENCODE_PHOTON_WASM_PATH` shim in `src/image/image.ts`) used by both `imagegen.ts` and `chroma.ts`. Files: `packages/opencode/src/plugin/openai/imagegen/imagegen.ts` (`saveImage`, `encodeJpeg`, `encodeWebp`, `uniqueStem`), `photon.ts` (new shared loader), `plugin.ts` (relative paths, save before output).

Works on both transports and with edits (`image_paths` + `transparent`). Clean for solid-edged subjects; wispy edges (hair/fur/glass/smoke) may fringe — documented in the model-facing `transparent` arg description and the skill's "Transparent backgrounds" section. Native `gpt-image-1.5 background:transparent` (true alpha for wispy subjects, API-key only) is deliberately left as a future opt-in so the default keeps the better gpt-image-2 image and works on OAuth. Perf: full 1536×1024 keys in ~110ms. Tests in `test/plugin/imagegen.test.ts` build a fixture via Photon and assert corners→transparent, subject→opaque, no green fringe. **Bright-rim halo fix (post first live test):** live cutouts showed a light/white halo because the image models paint a thin near-white "sticker outline"/rim-light glow where the subject meets the key color — that rim isn't key-colored, so pure chroma keying leaves it opaque (a chroma-key limit, not a port bug; Codex relies on an agent re-running with `--edge-contract`). Fixed unattended two ways: (1) `Chroma.PROMPT` now forbids outline/stroke/sticker-border/white-edge/halo/rim-light/glow/light-wrap around the silhouette; (2) new automatic `defringeBrightRim` pass (default on, `DEFRINGE_*` constants) erodes 2 one-pixel rings of any matte-boundary pixel that is bright (mean RGB ≥ 200) **and** desaturated (HSV S < 0.15), eating the grey/white rim while sparing saturated colored edges and thin features. Tuned offline on the real keyed PNG, confirmed on a fresh live gen (opaque white-rim px 2419→845, no visible halo over magenta). Genuinely-white subjects are the irreducible case → future `gpt-image-1.5` opt-in. Tests `defringe erodes…`/`defringe can be disabled` added (10 pass). Files: `packages/opencode/src/plugin/openai/imagegen/chroma.ts` (new), `imagegen.ts` (`Args.transparent`, transparent branch in `run`/`generateOrEdit`, `encodeWebp`), `plugin.ts` (`transparent` arg/schema/metadata/label), `imagegen-skill.md` (Transparent backgrounds section).
