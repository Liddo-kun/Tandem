# Android/PC Timing Bug Notes

## Summary

The duplicate assistant replies were caused by clock skew between the Android tablet web UI and the PC running the opencode server.

The web UI on Android generates a user `messageID` using the tablet clock. The server generates assistant message IDs using the PC clock. The server prompt loop currently uses lexicographic message ID ordering as a proxy for whether the latest user message has already been answered. Because message IDs encode timestamps, Android being ahead of the PC can make the user message ID sort after the assistant message ID, even though the assistant already answered that user message.

That makes the server think the user message is still unanswered, so it starts another assistant generation and persists a duplicate assistant reply.

## Evidence

The issue is not just a visual web UI rendering duplicate.

The local server API returned separate persisted assistant messages with:

- Different assistant message IDs.
- The same `parentID` pointing to the same user message.
- The same response text.
- Sequential creation/completion timestamps.

Example pattern from the session API:

```text
assistant 1:
id       msg_e2aea4b16001...
parentID msg_e2aea5005001...
text     Hi. How can I help with the repo today?

assistant 2:
id       msg_e2aea5361001...
parentID msg_e2aea5005001...
text     Hi. How can I help with the repo today?
```

Because the duplicates are present in API/session data, they are already persisted before the web UI renders them.

## Measured Clock Skew

Initial ADB midpoint measurements showed the Android tablet was about `+1.3s` to `+1.4s` ahead of the PC.

Example measurements:

```text
Android - PC midpoint: +1377 ms
ADB roundtrip: 165 ms

Android - PC midpoint: +1346 ms
ADB roundtrip: 113 ms
```

This is enough skew to make a client-generated user message ID sort after a server-generated assistant message ID.

## Relevant Web UI Path

The Android web UI uses the app frontend code.

Normal prompt submission creates a client-side message ID here:

```ts
// packages/app/src/components/prompt-input/submit.ts
const messageID = Identifier.ascending("message")

await input.client.session.promptAsync({
  sessionID: input.draft.sessionID,
  agent: input.draft.agent,
  model: input.draft.model,
  messageID,
  parts: requestParts,
  variant: input.draft.variant,
})
```

That ID is generated by the web UI clock:

```ts
// packages/app/src/utils/id.ts
function create(prefix: Prefix, descending: boolean, timestamp?: number): string {
  const currentTimestamp = timestamp ?? Date.now()
  ...
}
```

On Android, `Date.now()` uses the tablet clock.

## Relevant Server Path

The server accepts an optional client-provided message ID:

```ts
// packages/opencode/src/session/prompt.ts
const info: MessageV2.User = {
  id: input.messageID ?? MessageID.ascending(),
  role: "user",
  sessionID: input.sessionID,
  time: { created: Date.now() },
  ...
}
```

If the web UI sends `messageID`, the server uses the Android-generated ID.

The server then creates assistant IDs on the PC.

The prompt loop currently decides whether to exit with this condition:

```ts
// packages/opencode/src/session/prompt.ts
if (
  lastAssistant?.finish &&
  !["tool-calls"].includes(lastAssistant.finish) &&
  !hasToolCalls &&
  lastUser.id < lastAssistant.id
) {
  break
}
```

The unsafe part is:

```ts
lastUser.id < lastAssistant.id
```

That assumes message IDs generated on different devices are reliably ordered by real event order.

## Why TUI/Desktop Do Not Hit This

The CLI/TUI path does not send a client-generated `messageID` for normal prompts:

```ts
// packages/opencode/src/cli/cmd/run.ts
await client.session.prompt({
  sessionID,
  agent,
  model,
  variant: args.variant,
  parts: [...files, { type: "text", text: message }],
})
```

Because no `messageID` is sent, the server generates the user message ID using the PC clock:

```ts
id: input.messageID ?? MessageID.ascending()
```

That keeps user and assistant IDs on the same clock source, so the bad ordering assumption usually does not fail.

This explains why the bug shows up in the Android/web UI path but not in TUI or desktop-like local flows.

## Why Setting Android Behind By One Minute Made Things Worse

Setting Android far behind can create the opposite ordering problem.

If a new user message ID sorts before older messages, server code that derives the latest user/assistant by maximum message ID can misidentify the latest turn. That can make the session appear stuck or unresponsive.

The safe clock workaround is not “set Android far behind.” The safe workaround is “keep Android close to PC time, with a slight behind bias.”

## Temporary Clock Workaround

The best temporary target is a small negative Android offset:

```text
Android ~= 50 ms to 100 ms behind PC
```

Recommended script target:

```text
TargetOffsetMs = -75
ToleranceMs = 50
SampleCount = 9
IntervalSeconds = 30
```

Acceptable range with those settings:

```text
-125 ms to -25 ms
```

This keeps Android slightly behind but not so far behind that message IDs become stale relative to previous server messages.


Command to run it continuously:


The script:

- Uses `cmd alarm set-time`, which worked on the Y700.
- Measures offset with PC-before/Android/PC-after midpoint compensation.
- Uses multiple samples and the median to reduce ADB latency noise.
- Uses tolerance to avoid constantly chasing measurement jitter.

## Fix Options

### Option 1: Server Prompt Loop Fix

This is the best architectural correctness fix, but it is not the lowest-risk Tandem/mobile patch if applied casually as a one-line change without broader tests.

Change the stop condition from clock-derived ID ordering:

```ts
lastUser.id < lastAssistant.id
```

to the explicit parent-child relationship:

```ts
lastAssistant.parentID === lastUser.id
```

Full production change:

```diff
diff --git a/packages/opencode/src/session/prompt.ts b/packages/opencode/src/session/prompt.ts
@@
             lastAssistant?.finish &&
             !["tool-calls"].includes(lastAssistant.finish) &&
             !hasToolCalls &&
-            lastUser.id < lastAssistant.id
+            lastAssistant.parentID === lastUser.id
           ) {
             yield* slog.info("exiting loop")
             break
```

Why this is better:

- It fixes the invalid server assumption directly.
- It works for any client, not just Android web UI.
- It does not change API paths, payloads, SSE/WebSocket behavior, auth, or mobile rendering.
- The server already stores the correct relationship via `assistant.parentID`.
- It is a one-line production code change.

Important caveats:

- This only fixes the specific exit-condition failure where a finished assistant answered the latest user but sorts before that user because of cross-device clock skew.
- `MessageV2.latest()` still chooses `lastUser`, `lastAssistant`, and `lastFinished` by maximum message ID, so far-behind client IDs can still make the server choose the wrong latest user.
- Task and compaction detection also depends on ID ordering relative to the latest finished assistant.
- The one-line `parentID` fix assumes `assistant.parentID` is correct for all assistant messages in all relevant session histories, including migrated, imported, forked, compacted, errored, and interrupted sessions.
- A production-quality upstreamable server fix should be tested against normal prompts, tool calls, provider-executed tools, compaction, subtask handling, interrupted assistants, errored assistants, forks/imports, future-skewed client IDs, and past-skewed client IDs.

Why upstream may not have fixed it already:

- The common TUI/CLI path does not send client-generated user message IDs, so user and assistant IDs are generated on the same machine.
- Desktop/local users usually do not have the Android-webview-vs-PC clock split.
- Most browser clients have automatic network time close enough to the server.
- The current code comments around `MessageV2.latest()` assume `MessageID.ascending` is monotonic, and that assumption mostly holds when one machine generates all message IDs.
- The Android/APK remote web UI path makes a rare cross-device invariant violation much easier to hit.
- Large projects with many users still miss bugs at the boundary between client optimistic UI, server ID ordering, and device clock skew.

Optional regression test idea:

- Create a user message with a future-skewed ID.
- Create an assistant message with `parentID` equal to that user ID and `finish: "stop"`.
- Run `prompt.loop`.
- Assert it returns the existing assistant message and does not call the LLM again.

The test is many lines, but the actual production fix is one line.

### Option 2: Web UI Only Fix

This avoids the known Android/web trigger without touching server prompt-loop logic. Given the current evidence and the goal of keeping Tandem close to upstream OpenCode, this is the lower-risk practical fix for the Android/mobile path.

Normal prompt submission currently sends a client-generated `messageID`:

```ts
const messageID = Identifier.ascending("message")
...
messageID,
```

A web-only fix would stop sending `messageID` for normal prompts and let the server generate it:

```ts
await input.client.session.promptAsync({
  sessionID: input.draft.sessionID,
  agent: input.draft.agent,
  model: input.draft.model,
  parts: requestParts,
  variant: input.draft.variant,
})
```

Tradeoffs:

- Prevents Android clock-generated user IDs from reaching the server.
- Makes the web UI behave more like TUI/CLI for normal prompts: the server generates the user message ID on the PC clock.
- Avoids relying on a subtle prompt-loop invariant change in core opencode.
- More invasive in the app because optimistic UI currently depends on knowing `messageID` before the server responds.
- A minimal version could remove/disable optimistic user-message insertion for normal prompts.
- A polished version would use a local-only temporary ID and replace it when the real server message arrives.
- Does not fix the server bug for other clients that send future-skewed IDs.

This is the better Tandem/mobile patch if the priority is to avoid changing core server behavior. It removes the trigger that only the Android/web UI appears to hit, while leaving upstream prompt-loop semantics alone.

### Option 3: Clock Sync Workaround

This is useful short-term but is not a real product fix.

Pros:

- No repo source changes.
- Works immediately for the known Android tablet setup.

Cons:

- Fragile.
- Requires ADB access.
- Android automatic time is disabled.
- Drift or reboot can bring the problem back.
- Does not help other clients.

## Recommendation

Revised recommendation after comparing TUI/desktop behavior with the web UI path:

For Tandem right now, prefer Option 2: a web UI only fix that stops sending Android-generated `messageID` for normal prompts. This is lower risk because it makes the Android/web path match the TUI/CLI behavior where the server generates the user message ID on the PC clock.

The server prompt-loop fix remains the better architectural direction, but it should not be treated as a casual one-line patch unless backed by broader tests. The one-line change solves the duplicated-reply symptom for future-skewed user IDs, but other server logic still uses ID ordering to determine latest messages and pending work.

Recommended priority:

1. Web UI fix: do not send client-generated `messageID` for normal prompt submissions from `packages/app/src/components/prompt-input/submit.ts`.
2. Adjust optimistic UI to either wait for the server message or use a local-only temporary ID that is replaced by the real server message.
3. Add focused app tests for prompt submission payloads so normal prompts omit `messageID` while commands/special paths preserve expected behavior.
4. Later, consider a broader server robustness fix around turn detection and `MessageV2.latest()` with comprehensive prompt-loop tests.
5. Use the clock sync script only as a temporary workaround.
